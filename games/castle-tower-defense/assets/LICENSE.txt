Castle Tower Defense 3D — third-party asset licenses
======================================================

All assets in this directory are Creative Commons Zero (CC0). No
attribution is required, but credits are listed below as good practice.

That sentence is now true without qualification. It was NOT true between
the ADR-034-era Rodin import and 2026-07-31, and an earlier version of
this header asserted it anyway. The four non-CC0 files are gone; the
correction and the removal are both recorded under "MODELS — Hyper3D
Rodin generations (REMOVED)" below. ADR-039 D22 now has NO live
exceptions, and the spent clause is not available to any future asset as
precedent.

Policy of record: ADR-039 (docs/adr/039-ctd3-cc0-asset-expansion-policy-
and-monster-suite.md). Third-party art shipped from this directory must
be CC0 and must carry a per-file entry below. First-party art the
operator authored (e.g. /assets/forest-house-landscape.png) is outside
that policy and is deliberately not ledgered here.

  DOWNLOAD ROUTE — the fallback, and why (ADR-039 D25 route honesty):
    The pack page's Download button resolves to a Google Drive folder
    (id 18m4KpzpEzhC9wl7jzr6dUc0N8Jozr79C). Every per-file endpoint on
    that folder returned "Google Drive - Quota exceeded" on 2026-07-24
    (drive.google.com/uc, drive.usercontent.google.com/download, with
    and without a browser user-agent). The folder STRUCTURE enumerated
    fine via embeddedfolderview — Big/, Blob/, Flying/, each with a
    glTF/ subfolder — so the pack's CONTENTS (a model of each title
    below is in the pack) and its CC0 grant were both read off the
    source of record.
    Stated precisely, because the distinction matters to a future
    licence audit: no byte-level chain ties the downloaded files to
    the Quaternius Drive copy, because the Drive bytes were never
    obtainable. What is established is (a) a model of that title is in
    the CC0 pack, (b) each model's own poly.pizza page declares CC0,
    and (c) the bytes are internally consistent with Quaternius rig and
    naming conventions. That is strong corroboration, not byte-level
    confirmation. Anyone re-auditing should re-read each model page.
    The bytes therefore came from the ADR-039-sanctioned poly.pizza CC0
    mirror: https://static.poly.pizza/<ResourceID>.glb
    Per-file publicID + ResourceID are recorded below so any re-import
    is reproducible without re-deriving them.

  SUB-PACK NOTE: Ultimate Monsters ships three stylistic sub-packs whose
  rigs differ, which is why clip sets differ per file below:
    Big    — full-size monsters, ~46 nodes, 14 clips incl. Walk + Run
    Blob   — chibi/blob forms,   ~8 nodes,   9 clips incl. Walk + Jump
    Flying — winged/hovering,   ~16-41 nodes, 8 clips incl. Fast_Flying
  Sub-pack membership was determined per file by fingerprinting the
  armature name, clip set, node count and mesh names — not inferred from
  the model title. One superficially-matching candidate ("Demon",
  armature EnemyArmature, single Atlas material, doubly-prefixed clip
  names) was REJECTED by this check as belonging to a different
  Quaternius pack. Caveat on the fingerprint's strength: MATERIAL names
  are pack-wide rather than per-model, so they carry little identifying
  weight on their own — "Mushroom King" ships an Orc_Main material and
  "Ninja" ships a Birb_Secondary. The armature + clip-set + node-count
  signature is what actually discriminates.

  OPTIMIZATION (ADR-039 D25 — packing only, never restyling):
    @gltf-transform: resample -> dedup -> weld -> prune -> quantize
    (KHR_mesh_quantization, natively supported by three.js GLTFLoader,
    so no decoder script and no importmap change). Unused animation
    clips dropped; only the clips the game plays are kept. Materials
    are UNTOUCHED — Quaternius palette colours are the point, and these
    models carry zero textures (flat-colour materials only), which is
    why no texture atlas is imported. `skin.skeleton` is unset after
    pruning (an optional glTF hint; three.js builds its Skeleton from
    `joints`) because pruning can otherwise leave it pointing at a node
    that is no longer a common root — the glTF validator flagged
    exactly this on the blob rig.
    All nine files: glTF-Validator 0 errors.

  TOOLCHAIN: glTF-Transform v4.4.1 (recorded in each file's
  asset.generator). Quantization bit depths: position 12, normal 10,
  weight 8, texcoord 10 — note these are PRECISION settings, not size
  settings: 12- and 14-bit positions both pack into int16, so changing
  them does not change the byte size.

  ON THE TWO TRI COLUMNS BELOW — they are different measurements and
  neither is a typo:
    "page tris" is the statistic on the model's own poly.pizza page. It
        is a THIRD-PARTY figure about the upstream source, recorded for
        traceability only.
    "file tris" is the shipped .glb's own triangle count, measured by
        summing primitive index counts after load.
  They disagree by up to 1.7x (aggregate +31%: 33,388 page vs 43,652
  shipped), so do not size a perf budget off the page figure. The
  optimization passes cannot ADD geometry, so the upstream source must
  itself have had the higher count — the page statistic evidently
  describes something narrower. "draw calls" is the number of
  SkinnedMeshes per instance, which is what a frame actually pays:
  materials are deliberately untouched (ADR-039 D23), so each distinct
  material stays its own primitive.

        CLIP RENAME, and why it is part of the pipeline rather than a tweak:
        the source names its clips `CharacterArmature|<name>` and the import
        strips that prefix, because scene.js resolves ENEMY_VIS.moveClip with
        THREE.AnimationClip.findByName — an EXACT match. A prefixed clip
        therefore misses, falls through to the "first non-death clip"
        fallback, and plays the right animation only by ordering luck while
        warning on every spawn. Caught in-browser, not by the harness: the
        harness's enemy-vis-clips-resolve strips the prefix before comparing,
        so it is MORE PERMISSIVE than the runtime and passed the prefixed
        build. All nine models above already carry bare names.

  MEASURED-REALITY NOTE for whoever imports next. ADR-039 D25 called
  ~300 KB "a comfortable rather than aggressive ceiling" on the basis of
  one 232 KB spot-check. That premise did not survive the full import:
  every Big-pack model arrives OPTIMIZED at 257-321 KB, i.e. at or above
  the figure D25 cited as unoptimized, and their sources are ~2x that.
  The budget turned out near-binding, not comfortable. Plan ~300 KB per
  Big-pack model, not ~230 KB. The draw-call column is the other cost
  D25 did not model at all: 3-11 per instance versus 1 for the
  single-primitive kit meshes these replace.
  ADDENDUM (ADR-040): the note above is a BIG-pack observation and does not
  generalise. The Flying sub-pack is materially lighter — skirmisher2 99 KB,
  ghost2 139 KB, drake2 117 KB — so a flyer import has real headroom under
  the ~300 KB budget where a Big-pack import does not.

  model in `?test=roster` and READ THE CONSOLE before committing. The harness
  cannot see a clip-name mismatch (see the CLIP RENAME note above), and the
  runtime's fallback hides it behind a warning rather than a failure.

----------------------------------------------------------------------
  Files:    enemy_juggernaut.glb, enemy_slime.glb, enemy_mini_slime.glb,
            enemy_ghost.glb  — DELETED, no longer in this directory.
  License:  Hyper3D Rodin generation terms — a per-account commercial
            grant, NOT a public-domain dedication and NOT CC0.

  This entry is retained as a TOMBSTONE, not as a live ledger row. It
  stays because the four binaries remain reachable in git history, and a
  reader who finds a non-CC0 blob in this repo's past needs to be able to
  find out what it was and why. Deleting the entry along with the files
  would leave that question unanswerable.

  Provenance, as recorded when they were ledgered (best-effort per D24 —
  the generating session left no prompt or job record):
      glTF asset.generator : "Khronos glTF Blender I/O v5.1.19"
      mesh names           : RODIN_Juggernaut, RODIN_Slime,
                             RODIN_Slime.002, RODIN_Ghost
      rig                  : none (skins: 0, animations: 0 — static)
  The RODIN_ prefix is what identified them.

  WHY THEY ARE GONE. ADR-039 D22 grandfathered exactly these four
  filenames as an enumerated, closed exception, retained only as the
  rollback path for the roster swap, with one exit condition: the
  imported roster surviving an operator playtest WITHOUT A MODEL-LOADING
  REGRESSION. That condition is now discharged. The 2026-07-26 playtest
  (docs/handoffs/2026-07-26-roster-playtest.md) reported one or two
  creeps that "did not look animated" and did NOT identify the cause, so
  the note explicitly did not discharge D22 on its own. The sprint-10 X-3
  diagnosis settled it: driving the real render path across all six
  campaign maps, 11/11 roster types loaded with zero placeholders, 11/11
  resolved their moveClip exactly, and 11/11 ran a mixer. The defect was
  a procedural-layer suppression in syncEnemies, not a load failure — a
  class against which a rollback to these models is no remedy at all.
  Fixed in "ctd3: scene — procedural-layer suppression static-enemy fix".

  D22 now has NO live exceptions. This clause is spent and is explicitly
  NOT precedent: a non-CC0 asset arriving after ADR-039 is refused
  outright, and "we can ledger it honestly and delete it later" is
  reasoning that was available only to these four files, only because
  they were already shipped when the policy was written.
